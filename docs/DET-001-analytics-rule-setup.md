# DET-001 Microsoft Sentinel Analytics Rule Setup

This note documents how to turn the implemented DET-001 KQL logic into a Microsoft Sentinel scheduled analytics rule for the INC-001 validation exercise.

> This is a lab configuration guide. Confirm all settings against the tenant and Microsoft Sentinel interface before using them outside a controlled lab.

## Rule Identity

**Name:** `DET-001 - Repeated Failed Entra ID Sign-ins`

**Description:** Detects more than five invalid-password Microsoft Entra ID sign-in events associated with the same source IP address and user principal name within the analytics rule's configured lookback period.

**Severity:** Medium for the lab.

**MITRE ATT&CK:** Credential Access → Brute Force (T1110)

## Rule Query

Use the implemented DET-001 query without changing its detection semantics:

```kusto
SigninLogs
| where ResultType == "50126"
| summarize FailedAttempts = count() by IPAddress, UserPrincipalName
| where FailedAttempts > 5
| project IPAddress, UserPrincipalName, FailedAttempts
| order by FailedAttempts desc
```

## Suggested Lab Scheduling

For INC-001, use a short bounded rule window so the controlled test activity is evaluated promptly.

Suggested lab values:

- **Run query every:** 5 minutes
- **Lookup data from the last:** 10 minutes
- **Alert threshold:** Generate an alert whenever the query returns results

These are lab settings, not production recommendations.

The scheduled rule's lookback period provides the time boundary for the current lab query. Query-level time-window tuning is intentionally reserved for Issue #3.

## Entity Mapping

Where the Sentinel interface supports it, map:

- **Account:** `UserPrincipalName`
- **IP:** `IPAddress`

Entity mapping helps the incident surface the affected identity and source during investigation.

## Incident Settings

Enable incident creation from alerts generated by the analytics rule.

For the INC-001 lab, the goal is to produce a reviewable chain:

**SigninLogs → DET-001 scheduled rule → alert → Sentinel incident → investigation**

## Validation

After enabling the rule:

1. Generate the authorised six-failure test described in `../incidents/INC-001-repeated-sign-in-failures/README.md`.
2. Confirm the activity appears in `SigninLogs`.
3. Run DET-001 manually and capture E01.
4. Allow the scheduled rule to evaluate the data.
5. Open the resulting Sentinel incident and confirm the mapped account/IP correspond to the controlled test.
6. Capture E02.

## Important Notes

- Do not use a privileged production identity for the test.
- Do not increase failed attempts unnecessarily.
- If the tenant's lockout policy makes six failed attempts unsafe, stop and redesign the lab before testing.
- A matching rule result is an investigation signal, not proof of compromise.
- Production deployments require environment-specific thresholding, suppression/grouping decisions, exclusions and broader tuning.
